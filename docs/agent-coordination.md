# Bobo：从桌面宠物到能交接工作的 Agent 管家

研究与实现记录：2026-10-04。面向桌面端；日常仍是宠物和对话气泡，大页面只放任务历史、证据、用量与设置。

后续实现更新：已加入用户触发的任务接续、文件检查和跨尝试用量记录。首轮同模型小样本对照没有节省 Token，交接组反而增加约 37%。具体功能与边界见 `docs/workflow-release.md`；下文“尚未实现”是方案制定当时的状态。

## 判断

只把自然语言转发给 Codex、Claude Code、豆包，没有足够的工作优势。值得验证的产品承诺是：**任务中途换工具时，少丢进展、少重复劳动，交付时知道到底检查过什么、花了多少。** Bobo 陪伴用户的形象可以提高使用意愿；工作价值必须靠任务完成质量与实际成本证明。

目前没有证据表明 Bobo 比有经验的人选择 Agent 更好，也不能把这些问题称为“业界完全没人解决”。通信压缩、任务状态、预算和验证已有研究及工程实践。我们的机会是将它们做成跨工具、低打扰、可核查的个人桌面流程，并证明特定场景的收益。

## 协议解决互通，策略决定是否划算

[A2A 官方规范](https://a2a-protocol.org/latest/specification/)提供能力发现、任务状态、消息、产物和异步交互等标准。它能减少接入的重复工程，但不自动保证更聪明、更省 Token，现有 CLI 包装也不能因此宣称已实现 A2A。Bobo 可先对齐这些概念，待真实出现 A2A 服务接入需求时实现标准适配器。

内部先用可校验的 JSON 任务记录。格式的目标是防止遗漏状态和约束，不是因为 JSON 天然比自然语言省 Token。不要自创难读的“Agent 黑话”；也不把需要模型内部状态访问的潜在表示通信，作为闭源跨厂商工具的近期依赖。

LLM 用于理解需求、补齐交接摘要、解释结果；进程状态、文件变更检测、重复派发拦截、权限、计数、取消和预算判断用确定性代码。可以用强模型处理关键决策，避免每一次进度刷新都请求强模型。

## 首个闭环：任务接力与验收（待实现）

例子：用户让 CC 处理一个有明确交付标准的工作，途中遇到限额。Bobo 保存已有产物、已检查的事实、失败点和未完成清单；在用户已授权的工具范围内，将这一小份交接记录及必要产物交给 Codex。接收者先核对当前文件版本，再继续；完成后对照最初的标准检查，反馈通过项与遗留项。

这也适用于调研资料、表格清洗、文档交付等场景，但每项任务必须有相应的读写工具与可执行验收标准。豆包当前仅支持人工转交，不应展示为自动接力成员。

交接记录建议包含：

```json
{
  "schema_version": 1,
  "task_id": "stable-id",
  "attempt_id": "attempt-2",
  "parent_attempt_id": "attempt-1",
  "goal": "用户要求的交付物",
  "constraints": ["必须保留的用户约束"],
  "acceptance": [{"criterion": "具体检查条件", "status": "not_checked"}],
  "workspace_revision": "文件快照或 Git 版本标识",
  "observations": [{"claim": "已经确认的事实", "evidence_ref": "artifact-id"}],
  "artifacts": [{"id": "artifact-id", "path": "授权工作区内相对路径", "sha256": "内容指纹"}],
  "blocker": "已确认的停止原因；未知则保留未知",
  "next_action": "可以接着做的最小一步",
  "budget": {"remaining": null, "unit": "unknown"}
}
```

交接不迁移隐藏推理或另一家模型的内部会话状态。适配器支持原生会话恢复时优先同工具恢复；跨工具时基于产物和已验证状态重新建立上下文。摘要不是证据，接收方必须能按引用获取原始材料。内容过期、文件被用户修改、关键约束丢失时，先重新检查，不沿用缓存结论。

工作区同时只允许一个写入者；多个写任务需要隔离副本及显式合并流程。失败接力之前先确认前一执行进程停止。对派发/重试建立幂等标识，避免网络重试重复执行。权限不随交接扩大，结果文件中的文字不能变成管理指令。

状态至少区分：排队、执行中、受阻、执行结束待检查、验收通过、验收失败、取消。独立验收优先使用测试、文件结构、来源核对等可重复检查；没有客观判定器的工作保留用户验收，不能换一个模型说“看着不错”就当作通过。

调度器读取小型状态更新，仅在阶段改变、失败、用户询问或接续时调用模型。详情以引用和分页提供。不要让所有 Agent 不断讨论，也不要反复总结整段聊天。

## 怎样证明比用户自己选工具更有用

先选 30 个可复现任务，覆盖代码、资料整理、结构化文档三类；包含正常完成、受控限额/中断、约束改变、错误自报完成。固定初始文件、工具版本、模型、权限和最大预算；每个方案每题至少重复三次，随机顺序，避免缓存或先前产物污染。真实订阅限额不方便复现时注入相同停止点，并单独标注模拟与真实结果。

| 对照 | 含义 |
| --- | --- |
| A：用户直接选择工具 | 有经验的用户可选择并在相同条件下人工切换工具，记录人工操作时间；另报最强单 Agent 基线。不能拿故意受限的弱模型冒充用户基线。 |
| B：Bobo 简单转发 | 现有路由器，不使用接续记录或独立检查。分离宠物入口便利性与调度算法价值。 |
| C：Bobo 接续与验收 | 单执行者优先、按需交接、证据检查、总预算约束。与 A/B 使用相同候选模型和工具。 |

主要指标是固定预算内验收通过率、每个通过任务的总成本、人工干预次数/时间，以及恢复任务时重复执行的比例；辅以端到端耗时 P50/P95、约束遗失率和误报完成率。判断是否通过的检查不依赖系统自报，开放式输出由不知道实验组的评审评分。

总成本包含协调模型、工作 Agent、摘要、复核、失败、重试、缓存写入/读取以及有计费的工具。分别保留供应商 usage 原始字段与价格版本；未知消耗单列，不能计为零。订阅额度与 API Token 账单分开；缓存 Token 不重复累加。比较不同模型时不能简单用总 Token 代替费用。

建议预先登记一个产品门槛：相同质量范围内成本或人工干预明显下降，或相同预算下验收通过率提升；“明显”由样本规模与置信区间判定。初期可设探索目标为人工干预减少 30%，但它只是目标，不能作为已实现收益。先看失败案例和配对置信区间；30 题只够初步判断，承诺普适优势前需要更大任务集和真实用户数据。

同时做消融：移除交接记录、移除按需读取、移除验收分别重测。这样才能知道收益来自哪里。若简单任务 C 反而更贵，应直接走单 Agent 快速路径；如果整体没有收益，就不扩大多 Agent 编排。

## 本次已经落地的范围

- `.env` 已配置办公网络 Model Hub 域名、Azure 协议、API 版本 `2024-02-01` 和 `gpt-5.6-sol`。主进程使用 Azure SDK，每次请求生成 trace header；凭据不进入界面。
- 独立 SP `bobo-keeper-v1`：宠物阶段性格、简短自然的相处方式、能力诚实、少量按需派发、依据结果回答。SP 约束仍需代码与评测配合，不是质量保证。
- 新增 `read_task_result` 工具，最多每页 4000 字符，支持继续读取；不再只能查状态却看不到结果。Agent 输出明确标注未独立验收。
- 最近对话保留完整消息，限制最近 14 条/16000 字符，并告诉模型省略数量；不是无损记忆。单次输出上限默认 2048 Token，保留六轮请求/最多两项派发限制；这些不是端到端总预算。
- 真实接口的 `1+1` 返回 `2`，响应模型标识 `gpt-5.6-sol-2026-07-09`，用量 26 Token。独立临时存档中的角色问候为一次模型请求，任务查询为两次请求（工具调用与回传）；合计输入 3581、输出 58 Token，未派发工作 Agent，未改动用户养成存档。

尚未实现：跨 Agent 自动接续、任务合约持久化、独立验收执行器、总预算控制、学习型路由、跨工具自动额度读取。上述评测也尚未运行，因此现在不能宣称“比真人选 Agent 更好”或“节省 X% Token”。下一阶段以接续闭环和对照评测为主，先不扩展宠物社交或更多 Agent 品牌。

验证：26 项自动化测试通过；TypeScript/Vite 构建通过；真实 Electron 冒烟测试通过，覆盖桌面气泡、聊天工具调用、CLI 任务、手动转交、取消及重启存档恢复。它们验证功能正确性，不代表完成了上述产品对照评测。
